# System Architecture

**System:** ASOS (AI Sales Operating System)
**Document Status:** Approved v1.0
**Target Audience:** Engineering, Product, AI Development

---

## Purpose

The purpose of this architecture is to fundamentally decouple data storage from business intelligence. Traditional dealership software (CRMs, DMS) intertwines the database with rigid, hardcoded workflows.

ASOS exists to establish a dedicated, intelligent operating layer above existing systems of record. This document outlines how ASOS observes data, applies dealership-specific knowledge, reasons through complex scenarios, and orchestrates specialized AI agents to assist human operators. It is the blueprint for building an AI-native system that thinks before it acts.

---

## Architecture Principles

Our technical decisions are governed by the following core principles:

* **AI First:** The system assumes the presence of reasoning capabilities. We do not build static rule-based IF/THEN trees; we build dynamic contexts for Large Language Models (LLMs) to evaluate.
* **Knowledge Before Code:** Dealership expertise—how to handle a trade-in, how to negotiate, how to prioritize leads—is stored as readable text (Markdown) rather than hardcoded logic. This allows domain experts to update the system's behavior without deploying code.
* **Decision Intelligence before Automation:** Automation without intelligence scales mistakes. ASOS must compute the correct decision before it attempts to automate the resulting task.
* **Human in the Loop:** AI proposes; humans dispose. The system is designed to remove administrative friction, but human operators retain ultimate authority over financial and customer-facing decisions.
* **Explainable AI:** No black boxes. Every recommendation generated by the system must include a clear, traceable explanation (the "Why") linked to specific data points and business rules.
* **Modular Design:** Components, LLMs, and external APIs must be entirely decoupled. If we swap our primary LLM provider, the system architecture remains intact.
* **Scalability:** The architecture must handle single-deal deep reasoning just as efficiently as it processes end-of-month portfolio-wide forecasting.
* **Continuous Learning:** The system architecture natively supports feedback loops. Human corrections to AI recommendations must route back into the Knowledge Layer to improve future outputs.

## High-Level Architecture

ASOS is not a monolithic application. It is a strictly decoupled, seven-layer architecture designed to transform raw data into executed human decisions. Data flows upward from external sources, is contextualized by dealership knowledge, processed by the central AI brain, delegated to specialized agents, and ultimately authorized by human users.

---

## Layer 1 — External Data Sources

This layer represents the system's sensory inputs. ASOS does not own this data; it observes, reads, and writes to these external systems. By treating all data sources as interchangeable inputs, ASOS remains platform-agnostic.

**Supported Data Sources:**

* Customer Relationship Management (CRM) databases
* Dealer Management Systems (DMS)
* Inventory Management Systems (New and Used)
* Finance & Insurance (F&I) Portals
* Dealership Website Analytics & Lead Forms
* Communication Channels: WhatsApp, Email, Phone/Voice Transcripts
* Google Sheets & Excel (Legacy/Ad-hoc data structures)
* *Future Integration Point:* Standardized OEM and third-party dealer APIs.

### Data Ownership and Authority

ASOS distinguishes between:

- External Systems of Record.
- ASOS Canonical Projections.
- ASOS Authoritative Workflow States.
- Derived Intelligence.
- Authoritative Human Decisions.

External authority is field-specific and deployment-specific. ASOS must not treat a normalized projection, AI recommendation, or pending outbound command as externally confirmed without authoritative evidence.

## Layer 2 — Knowledge Layer

**This is the most critical layer in ASOS.** It contains the dealership's operational DNA.

Instead of writing custom Python or Node.js logic for every dealership edge case, we externalize the logic into the Knowledge Layer. This allows the AI Brain to dynamically read the rules before making a decision. **This layer contains dealership expertise, NOT code.**

**Components:**

* **Product Vision:** The foundational goals and operational boundaries of ASOS.
* **Constitution:** The unbreakable behavioral guardrails for the AI (e.g., "Never approve a discount below invoice").
* **Playbooks:** Step-by-step guides for specific scenarios (e.g., "End of Month Used Car Liquidation").
* **Business Rules:** The logical parameters governing operations.
* **Documentation:** System definitions and API schemas.
* **Prompt Library:** Version-controlled system prompts and few-shot examples.
* **Glossary:** Standardized definitions of automotive terminology to prevent AI hallucination.
* **Operational Knowledge:** Historical dealership performance data and institutional memory.

---

## Layer 3 — Context Layer

The AI Brain should never receive the entire Knowledge Layer. Providing too much information degrades reasoning and increases token costs. The Context Layer dynamically retrieves only the relevant knowledge required for the current decision.

**Strict Rule:** The Context Layer does not perform reasoning and does not make business decisions.

Its sole responsibility is to assemble the minimum high-quality context required by the AI Brain.

**Responsibilities:**

* Context Retrieval
* Semantic Search
* Retrieval-Augmented Generation (RAG)
* Business Rule Selection
* Playbook Selection
* Customer Context Assembly
* Conversation History Retrieval
* Inventory Context
* Deal Context

**Why this layer exists:**
This layer reduces hallucination, improves accuracy, reduces token usage, and provides only decision-relevant information to the AI Brain. By acting as an intelligent filter, it ensures the AI always has the exact context it needs, without the noise of unrelated dealership policies.

---

## Layer 4 — AI Brain

The AI Brain is the central reasoning engine of ASOS. It acts as the routing and computation hub.

**Strict Rule:** The Brain *never* executes actions directly. It only thinks, plans, and delegates.

**Responsibilities:**

* Analyze
* Reason
* Prioritize
* Forecast
* Explain
* Recommend
* Select the appropriate AI Agent

---

## Layer 5 — AI Workforce

The AI Workforce consists of specialized, domain-specific AI Agents. Instead of one massive prompt trying to do everything, ASOS uses a multi-agent architecture. Agents collaborate instead of working independently, passing context to one another, and executing specific mandates delegated by the Brain.

**The Agent Roster:**

* Morning Brief Agent
* Sales Director Agent
* Lead Qualification Agent
* Follow-up Agent
* Forecast Agent
* Inventory Agent
* Finance Agent
* Delivery Agent
* Customer Success Agent
* Management Agent

---

## Layer 6 — Human Layer

The human operator is the absolute authority in the ASOS architecture. Humans always make final business decisions. The system is designed to augment human capacity, not replace it.

**Users include:**

* Sales Consultant
* Sales Manager
* General Sales Manager
* Dealer Principal
* Owner

---

## Layer 7 — Feedback & Learning Layer

Every human action becomes new organizational knowledge. ASOS continuously evolves from dealership experience.

**Examples:**

* Human overrides AI recommendation
* Deal won
* Deal lost
* Customer rejected offer
* Manager edited pricing
* Sales Consultant changed follow-up timing

These outcomes are stored as organizational feedback.

Updates to Business Rules, Playbooks, Prompt Library, or any Knowledge Layer asset always require human review and approval before becoming part of the Knowledge Layer.

This preserves Human-in-the-Loop governance while allowing continuous organizational learning.

## Design Principles

The engineering execution of ASOS must adhere to these traits:

* **Simple:** Avoid over-engineering.
* **Modular:** Any layer or agent can be replaced without bringing down the system.
* **Replaceable:** The architecture must allow us to switch providers instantly.
* **Observable:** Engineers must be able to trace the exact prompt and data state.
* **Scalable:** Handles asynchronous concurrent agent operations.
* **Transparent:** System state and reasoning must be visible.
* **AI Native:** Built from the ground up for LLMs.

## Repository Structure

ASOS treats knowledge as code. Our GitHub repository is organized to manage operational logic identically to how software companies manage source code.

```text
/ASOS
├── 00_Constitution/
├── 01_Playbooks/
├── 02_Business_Rules/
├── 03_Prompts/
├── 04_Data/
├── 05_Documentation/
├── 06_Assets/
└── 07_Knowledge_Base/
```

**Why this structure exists:**
By isolating the Knowledge Layer into distinct, version-controlled directories, we allow non-engineers to push updates to the AI's behavior via Pull Requests.

## Future Architecture

While v1.0 of ASOS is tailored for a single dealership ecosystem, the architecture is natively multi-tenant.

The Context Layer allows ASOS to support multiple dealerships without sending unnecessary knowledge to the AI. Each dealership loads only its own context while sharing the same centralized AI Brain. This means ASOS can grow from one dealership into a massive multi-dealership platform without changing its underlying architecture.
